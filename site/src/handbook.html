01
The confusion

A branch is not a folder

The fear: "When I make a branch, where does the folder go? And why did my files change when I switched?"

The truth: A branch makes no new folder. You stay in the same folder — Git just swaps what's inside the files to match the branch you're on.

  1. Know where you are. Remember this — it will never change during the drill.

    # prints your one and only project folder
pwd
ls

  2. Make a branch and leave a note in it.

    git checkout -b timeline-a
echo "I am on TIMELINE A" > scratch.txt
git add scratch.txt
git commit -m "Timeline A note"
cat scratch.txt      # -> I am on TIMELINE A

  3. Start a different timeline from main.

    git checkout main
git checkout -b timeline-b
echo "I am on TIMELINE B" > scratch.txt
git add scratch.txt
git commit -m "Timeline B note"
cat scratch.txt      # -> I am on TIMELINE B

  4. The magic. Jump between branches and watch the same file change.

    git checkout timeline-a
cat scratch.txt      # -> I am on TIMELINE A
pwd                  # -> SAME folder as step 1

git checkout timeline-b
cat scratch.txt      # -> I am on TIMELINE B
pwd                  # -> STILL the same folder
What just happened: You never left your folder, and no new folder appeared. There's one scratch.txt on disk — switching branch rewrote it in place. A branch is a parallel timeline of the same folder, not a place on disk.
💡 In VS Code / Cursor: the branch name is in the bottom-left corner. Click it to switch — the file contents change, the file tree never sprouts a new folder.
02
The confusion

Staging — choose what goes in

The fear: "Why two steps — add then commit? I just want to save. And when an agent edits 8 files, how do I save only the part I want?"

The truth: Staging (git add) is you choosing exactly what goes into the snapshot — not everything you touched. It's how one messy folder becomes one clean save point.

  1. Start clean on your own branch.

    git checkout main
git checkout -b staging-drill

  2. Change two unrelated things.

    echo "A real change I want to keep" > keep-me.txt
echo "TODO: half-finished, not ready" > not-ready.txt
git status   # both show as changed; nothing staged yet

  3. Stage only the file you're proud of, then read git status carefully.

    git add keep-me.txt
git status
# keep-me.txt   -> "Changes to be committed"  (going in) ✅
# not-ready.txt -> "Changes not staged"      (left out) 🕗

  4. Commit — only the staged file goes in.

    git commit -m "Add the change I actually finished"
git status   # not-ready.txt is still here, untouched, waiting
What just happened: git add = "this belongs in my next snapshot." git commit = "take the snapshot of what I staged." Two steps exist so you can make clean, single-purpose commits even when your folder is a work-in-progress mess. Want everything? git add .
💡 When an agent changed a pile of files: run git status first, then git add only the files that belong to this change. Review before you save — like reading a diff before approving it. In VS Code, the + next to a file in the Source Control panel is git add.
03
The monster

The pull conflict

The fear: "I ran git pull and the terminal filled with CONFLICT and weird arrows. I broke it."

The truth: You broke nothing. Someone changed the same line you did; Git can't guess who's right, so it stops and asks you. That's all a conflict is — a polite question.

  1. On your branch, set a line.

    git checkout main
git checkout -b pull-drill
echo "The best snack is: pizza" > snack.txt
git add snack.txt
git commit -m "Snack = pizza"

  2. Play the teammate: change the same line on main.

    git checkout main
echo "The best snack is: sushi" > snack.txt
git add snack.txt
git commit -m "Snack = sushi"

  3. Back on your branch, pull main in — and hit the conflict.

    git checkout pull-drill
git merge main
# CONFLICT (content): Merge conflict in snack.txt
git status   # it literally tells you what to do next

  4. Open snack.txt and read the question Git is asking.

    <<<<<<< HEAD
The best snack is: pizza        # your version
=======
The best snack is: sushi        # their version
>>>>>>> main

  5. Resolve: delete the three marker lines, keep the text you want (here, keep both), then save + commit.

    # file now just reads: The best snack is: pizza AND sushi
git add snack.txt
git commit -m "Resolve snack conflict: keep both"
git status   # -> working tree clean 🎉
What just happened: A conflict isn't an error — it's a pause for a human decision Git can't make safely. The fix is always the same: open the file → delete the markers → keep what you want → add + commit.
🧯 Escape hatch: not in the mood? git merge --abort puts everything back exactly as before. Nothing lost. Breathe, try again later.
💡 In VS Code / Cursor: conflicted files get an "Accept Current / Incoming / Both" button bar right above the conflict. Same three choices, clickable.
04
The trap

The giant branch (and the way out)

The trap: One branch, two weeks, everything piled in — a redesign, three fixes, a half-done experiment. Now nobody wants to review it and you can't ship any part alone.

The lesson: One branch = one thing. Small branches merge fast; giant branches rot. You'll build the monster on purpose, then learn the way out.

  1. Build the monster: pile three unrelated changes onto one branch.

    git checkout main
git checkout -b everything-branch
echo "New homepage headline" > copy.txt
git add copy.txt && git commit -m "Change homepage copy"
echo "Fix: wrong button color" > bugfix.txt
git add bugfix.txt && git commit -m "Fix button color"
echo "Experiment: dark mode??" > experiment.txt
git add experiment.txt && git commit -m "WIP dark mode"

  2. Feel the trap. The copy fix is ready; the experiment isn't — but they're welded together.

    git log --oneline   # three unrelated things, one branch

  3. The way out: start a fresh, small branch for the one thing that's ready.

    git checkout main
git checkout -b ready-copy-fix

  4. Copy just that commit across with cherry-pick.

    git log everything-branch --oneline   # copy the id for "Change homepage copy"
git cherry-pick <that-id>
git log --oneline   # just the copy fix, reviewable today
What just happened: The unfinished parts were holding the finished part hostage. You're never stuck — cut a small branch and cherry-pick the ready commit onto it. Push that, open a PR, and let the messy experiment wait.
✅ The habit that prevents all of this: before a new thing, start a new branch from an up-to-date main. Push and open a PR when that one thing is done. Then start fresh. Small and often beats big and scary.
05
The unlock

A PR is a conversation

The confusion: "I left a comment on GitHub but didn't really get that it lives on a branch's changes. I think in conversations, not branches."

The good news: A PR is a conversation — a comment thread attached to the actual change instead of floating next to it. You already do this in Docs and Figma.

  1. Push a small change on a branch. (This drill uses GitHub in the browser — you'll need push access or a fork.)

    git checkout main
git checkout -b pr-convo-drill
echo "- 🗣️ [your name] joined the conversation" >> wall.md
git add wall.md
git commit -m "Add my line to the wall"
git push -u origin pr-convo-drill

  2. Open the Pull Request — click the link the terminal prints, or hit "Compare & pull request" on GitHub. Give it a title, create it.

  3. Be the reviewer on your own PR. Open Files changed, hover your new line, click the blue +, leave a comment like "add an emoji?", then Request changes. Notice: the comment pins to the exact line — not a lost Slack DM.

  4. Reply the Git way — with a commit. Edit the line, then:

    # add the emoji to your line in wall.md, then:
git add wall.md
git commit -m "Address review: add emoji"
git push   # same PR updates itself — no new PR

  5. Resolve & merge. Mark the comment Resolved, click Merge pull request. The whole thread — ask, fix, resolution — stays attached to history forever.

What just happened: A PR bundles a branch's changes and the conversation about them into one place — that's the feature, not a technicality. "Being on a branch" isn't bureaucracy; the branch is what the conversation is about. You reply by pushing another commit.
🧹 After merging: click GitHub's "Delete branch" button. A short, merged, deleted branch is the whole point of Drill 4.
